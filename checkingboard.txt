================================================================================
CHECKINGBOARD PROJECT - MASTER CONTEXT & SPECIFICATION
================================================================================
This file serves as the living context and specification document for the
CheckingBoard dispatch application. Whenever any new feature or change is added,
it must be documented in this file.

--------------------------------------------------------------------------------
1. PROJECT OVERVIEW
--------------------------------------------------------------------------------
CheckingBoard is a dynamic, Excel-inspired fleet dispatch tracker built for
dispatchers and fleet managers. It categorizes truck drivers by operational
status in real-time, organizes them by carrier/company group, and provides
an Excel workbook tab experience pinned at the bottom of the window.

--------------------------------------------------------------------------------
2. TECH STACK & TOOLS
--------------------------------------------------------------------------------
- Frontend: Vue 3 (Composition API with <script setup>)
- Build Tool & Dev Server: Vite 6 (ultra-fast HMR and building)
- Styling: Tailwind CSS 3 + PostCSS + Autoprefixer
- Icons: Native Unicode & SVG icons
- Database, Accounts & Live Sync: Supabase (PostgreSQL + Supabase Auth + Realtime)
  - one shared database for every team, configured only through env variables
- Runtime: Node.js v24 LTS + npm (build tooling only; there is no app server)
- One-Click Launcher: start.bat (Windows batch script)
- GitHub Repository: https://github.com/nurillo-madaminov/CheckingBoard.git (branch: main)

--------------------------------------------------------------------------------
3. DATABASE ARCHITECTURE: ONE SHARED SUPABASE DATABASE
--------------------------------------------------------------------------------
There are no solo / team modes and no in-app database connection screen.
Every team and every dispatcher works in ONE Supabase database, and nothing
operational (companies, drivers, notes, statuses, activities, accounts) is stored
in the browser.

A. CONFIGURATION (ONCE, ON THE HOSTING PLATFORM):
- The frontend reads the database ONLY from build-time env variables, set where the
  frontend is built/deployed (Vercel, Netlify, etc.), then rebuilt:
    VITE_SUPABASE_URL=https://your-project.supabase.co
    VITE_SUPABASE_ANON_KEY=your-anon-public-key
- If they are missing, the app shows a "not connected to its database" setup
  message instead of the sign-in screen.
- src/services/supabaseClient.js creates the single client from these variables.

B. HOW A TEAM WORKS:
1. A manager opens the app and clicks "Create a Team" (team name, their name,
   username, password). They become that team's manager and are signed in.
2. The manager opens Team (sidebar) -> Members and creates logins (username +
   password) for each staff member, then gives them those credentials.
3. Staff sign in with that username and password. Everyone in the team sees and
   edits the same fleet; every action is recorded in the same database.

C. DATA ISOLATION BETWEEN TEAMS:
- companies, drivers and activities carry team_id. Row Level Security (RLS) in the
  database limits every read and write to the signed-in user's team; team_id is
  filled in automatically on insert. Anonymous visitors can read nothing.
- Deactivated users lose access immediately (RLS) and cannot sign in (Auth ban).

D. LIVE SYNC:
- Supabase Realtime postgres_changes on companies and drivers: any check, sign,
  status change, note or reorder by one dispatcher appears on teammates' screens.
  A broadcast (fleet_reset) adds the "Fleet reset to READY by another dispatcher"
  toast. The top bar shows the team name with a green dot while live.

E. BROWSER STORAGE:
- Only the Supabase login session (so you stay signed in) and your personal bottom
  tab order ('checkingboard_tabs_order_v1') are kept in the browser.

F. EXISTING FLEET (10 carrier companies / 196+ drivers):
- Data created before team accounts existed belongs to the legacy team 'team-1'.
  After creating your team in the app, move it into your team once in the SQL
  Editor:  SELECT public.claim_legacy_fleet('your-username');
- supabase_schema.sql no longer seeds drivers (the old seed was out of date and
  re-running it would have overwritten live edits).

4. TABLE STRUCTURE & LOCKED COLUMNS
--------------------------------------------------------------------------------
The dynamic table consists of 5 fixed-width columns with zero jitter:
1. # (Order Number):
   - Fixed 56px width (Col 0).
   - Sequential Excel-style row number (1, 2, 3...) for both drivers and companies.
   - Acts as the ONLY drag handle (with grip indicator ⠿) for drag-and-drop reordering.
2. Driver (Unit - Name):
   - Fixed 320px width (Col 1).
   - Formatted as "[unit] - [driver name]" when unit is present, or "[driver name]".
   - Text selection is preserved. Clicking name selects the row without opening edit modal.
3. Sign:
   - Fixed 140px width (Col 2).
   - Dropdown with SIGNED / NO SIGN options.
4. Status:
   - Fixed 190px width (Col 3).
   - Operational statuses: AT PU, AT DEL, COVERED, GOING DEL, READY, SHOP, HOME, INACTIVE.
5. Notes:
   - Flexible remaining width (Col 4).
   - Inline text input with auto-save on blur / enter.

8. DYNAMIC ROW AGING COLORS (WORKFLOW FRESHNESS SYSTEM)
--------------------------------------------------------------------------------
- Row background colors are dynamically calculated based on time elapsed since last check
  (lastCheckedAt timestamp), making dispatch workflow highly visible:
  * 0h (Newly checked): Fresh Green (rgb(220, 252, 231))
  * 1h - 2.5h: Aging Yellow (rgb(254, 249, 195))
  * 2.5h - 4h: Warning Orange (rgb(254, 215, 170))
  * 4h+ (or never checked): Overdue Red (rgb(254, 226, 226))
- Hover "✓" Quick Check Button: Dispatchers can click the "✓" button in the driver
  row hover actions to instantly refresh that driver line back to green.
- Modifying sign or status also automatically updates lastCheckedAt.
- Note Editing Does NOT Mark Checked: Editing or adding notes does NOT update lastCheckedAt,
  preventing notes changes from unintentionally turning a driver row green.
- Custom row highlight colors from the 🎨 palette take precedence if applied.
- Global Real-Time Aging Synchronization: When any dispatcher clicks the "✓" quick check
  button or updates a driver, the updated `last_checked_at` timestamp is instantly written
  to Supabase and broadcasted via WebSockets (`driver_updated`). All other dispatchers'
  screens update that driver in-place in milliseconds without reloading, turning the row
  Green simultaneously and aging together in real-time across all browser windows.
- Added `last_checked_at TIMESTAMPTZ` column and `REPLICA IDENTITY FULL` to `supabase_schema.sql`,
  with resilient fallback updates in `supabaseService.js`.

9. DAILY US EASTERN TIMEZONE SIGN RESET
--------------------------------------------------------------------------------
- Whenever the date changes in US Eastern Timezone (EST/EDT, America/New_York),
  all drivers' sign status automatically resets to 'NO SIGN'.
- Decided by the database (public.run_daily_sign_reset), once per team per US
  Eastern day: the first dispatcher online after midnight triggers it and teammates
  receive the change live. Checked on sign-in and every 60 seconds.
- teams.last_sign_reset_date stores the last reset date (no browser storage).

--------------------------------------------------------------------------------
10. RESET TO READY (RED) BUTTON & GLOBAL REAL-TIME SYNCHRONIZATION
--------------------------------------------------------------------------------
- The reset button in the top bar (next to Status Colors) resets all active drivers' status
  to 'READY' and clears `lastCheckedAt` to null.
- Global Real-Time Sync Across All Users: When any dispatcher clicks the reset button,
  it executes a PostgreSQL update on Supabase (`UPDATE drivers SET status = 'READY', last_checked_at = NULL WHERE status != 'INACTIVE'`)
  and sends a WebSockets Realtime broadcast (`fleet_reset`).
  All other active dispatchers automatically receive the event, re-fetch the fleet,
  update their rows to READY and Red simultaneously, and receive a toast alert:
  "Fleet reset to READY by another dispatcher".
- INACTIVE Drivers Excluded: Drivers with `status: 'INACTIVE'` are deliberately preserved
  as INACTIVE across the entire database. They remain strictly in the INACTIVE tab
  and do NOT get shown on the main CHECKING BOARD tab.
- This immediately marks all active driver rows in Red (Needs check ASAP / Overdue), giving
  dispatchers a synchronized clean slate for daily check rounds without altering inactive profiles.

14. ACTIVITY TRACKING, STAFF ACCOUNTABILITY & HISTORICAL DATA INTEGRITY
--------------------------------------------------------------------------------
CheckingBoard features a dedicated Activity Log and Manager Analytics dashboard
providing end-to-end staff accountability, immutable audit trails, and permanent
historical data preservation across operational driver/company deletions.

A. REQUIRED ACTIVITY RECORD SCHEMA & HISTORICAL SNAPSHOTS:
Each activity log record contains:
- `id`: Unique activity identifier (e.g., "act-1740000000-xyz").
- `staff_user_id`: ID of the authenticated staff member who performed the action.
  Derived strictly from the server/session authentication context (never trusted from
  arbitrary frontend request payloads).
- `staff_name_snapshot`: Staff member's display name at the time of the action.
  Preserved permanently so that historical records remain understandable even if
  the staff member's display name changes later.
- `driver_id`: Nullable foreign key referencing public.drivers(id) with ON DELETE SET NULL.
- `driver_name_snapshot`: Historical driver name and unit (e.g. "101 - Pervez Adnan")
  captured at the time of action.
- `company_id`: Nullable foreign key referencing public.companies(id) with ON DELETE SET NULL.
- `company_name_snapshot`: Carrier group name at the time of action.
- `action_type`: Type of activity performed:
  * SHIFT: Open shift
  * CYCLE: Open cycle / cycle check
  * FIX_LOG: Fix driver logs
  * BREAK: Driver rest / break
  * TRANSFER: Transfer driver to another company
  * STATUS_CHANGE: Change driver operational status (e.g. READY -> AT PU)
  * QUICK_CHECK: Hover ✓ quick check (refresh line to green)
  * DRIVER_CONNECTED: Driver mobile / TT ELD connection
  * DRIVER_ADDED: New driver added to fleet
  * DRIVER_DELETED: Operational driver deletion audit log
  * COMPANY_DELETED: Operational company deletion audit log
- `action_at`: UTC timestamp of the activity.
- `extra_note`: Optional context or notes.
- `created_at`: Database record creation timestamp.

B. ACTIVITY LOG TABLE INTERFACE & ROLE-BASED ACCESS CONTROL (RBAC):
The Activity Log page displays the 6 required columns:
| Order | Staff Member | Driver Name | Action Date and Time | Action | Extra Note |
1. Role-based visibility:
   - Managers: View all team-wide activity logs. Can filter by staff member,
     driver, action type, company (active or deleted, with suggestions), and date
     range (US Eastern day boundaries).
   - Staff Members: Can view ONLY their own activity records. Cannot view other
     dispatchers' activities.
2. Historical Name Fallback:
   - Displays historical staff snapshot name with fallback to "Unknown Historical Actor"
     for legacy records.
   - Displays historical driver name with a prominent "Deleted" badge if the driver
     is no longer in the active operational fleet.

C. HISTORICAL RETENTION & DELETION RESILIENCE:
- When a manager deletes a driver:
  * Operational driver is removed from the active fleet view.
  * All historical activity records previously associated with that driver are
    100% PRESERVED.
  * driver_id is set to NULL via ON DELETE SET NULL; driver_name_snapshot and
    company_name_snapshot remain permanently intact.
  * Deleting a driver never decreases manager activity totals or distorts reports.
- When a manager deletes a company:
  * Operational company is removed from active fleet.
  * Associated activity logs are NOT cascade-deleted.
  * Old activities remain searchable and understandable.
- Staff Account Deactivation:
  * Deactivating or removing a staff account does NOT delete their historical logs.
  * Historical display name snapshot remains visible in all past logs.

D. ROW-LEVEL SECURITY (RLS) POLICIES ON SUPABASE (supabase_schema.sql):
- Helpers: public.current_team_id() and public.is_team_manager() read the signed-in
  user's active profile (security definer).
- public.teams / public.staff_profiles: members read their own team / roster only.
  No direct writes: accounts change only through the functions in section 15.
- public.companies / public.drivers: members read and write rows of their own team;
  a driver can only point at a company of the same team.
- public.activities:
  * SELECT: staff read only their own records; managers read their whole team.
  * INSERT: a BEFORE INSERT trigger (activities_stamp_actor) overwrites
    staff_user_id, staff_name_snapshot, team_id, action_at and created_at from the
    session, and takes driver/company name snapshots from the live rows, so a
    client cannot forge who did what or when.
  * UPDATE / DELETE: no policy and no privilege. The audit trail is immutable.

E. MANAGER DASHBOARD & ANALYTICS RULES:
- Aggregates activity metrics directly from immutable activity records rather than
  current fleet state.
- Metrics include:
  * Total activities per staff member.
  * Shift, break, cycle, Fix Log, driver connection, status change, and transfer counts.
  * Daily, weekly, and monthly activity timeline totals.
  * Custom date-range reports.
- Timezone handling:
  * Timestamps are stored in UTC.
  * Daily/weekly/monthly grouping boundaries are calculated using the configured
    reporting timezone (America/New_York EST/EDT).

F. DATABASE SETUP SCRIPT:
- Single script: `supabase_schema.sql` (supabase_activities_migration.sql is
  superseded and empty). Run it in Supabase Dashboard -> SQL Editor. It:
  1. Creates or upgrades teams, staff_profiles, companies, drivers, activities
     in place, keeping all existing rows; foreign keys use ON DELETE SET NULL.
  2. Removes the old plain-text password column and deactivates the old demo
     profiles (Manager Sarah / Staff John / Staff Alice), whose names stay on
     historical activity records.
  3. Replaces the old "public" policies with the team RLS above.
  4. Adds the account / daily-reset / claim functions and Realtime publication.
- Safe to run again after future updates.

G. AUTOMATED TESTING:
- Test suite: `tests/supabase_accountability.test.js`, run against a real Supabase
  TEST project that has supabase_schema.sql applied (each run creates new logins):
    TEST_SUPABASE_URL=... TEST_SUPABASE_ANON_KEY=... npm test
  Without those variables the suite is skipped.
- 13 tests covering the original required scenarios on the real database:
  1. Staff A actor accountability
  2. Staff B actor accountability
  3. Prevention of forged actor IDs
  4. Manager staff filtering & staff own-record restriction
  5. Immutable staff name snapshots across account display name changes
  6. Driver deletion activity preservation
  7. Company deletion activity preservation
  8. Searchability of deleted entities
  9. Staff account deactivation resilience
  10. Dashboard statistics accuracy across operational deletions
  11. Rejection of direct PUT/DELETE API requests (403 Forbidden)
  12. Existing CheckingBoard functionality regression testing
  13. Database migration backward compatibility & unknown actor safety

15. TEAM REGISTRATION, USERNAME/PASSWORD AUTH & MANAGER STAFF PROMOTION
--------------------------------------------------------------------------------
A. ACCOUNTS ARE SUPABASE AUTH USERS:
- Passwords are bcrypt-hashed by Supabase Auth; the app never stores them.
- Usernames: 3-32 characters (letters, numbers, dot, dash, underscore), unique
  across the database. Username "nick" signs in as the internal address
  nick@checkingboard.internal (never emailed; the app maps it automatically).
- Accounts are created only by database functions, so public sign-up must be OFF:
  Supabase -> Authentication -> Sign In / Providers -> "Allow new users to sign up".

B. SIGN IN SCREEN (`src/components/LoginView.vue`):
- Username + Password + "Sign In to Dispatch". No demo accounts.
- Clear messages for wrong credentials and deactivated accounts.
- Sessions persist across reloads until "Sign Out".

C. "CREATE A TEAM" (CREATOR BECOMES MANAGER): rpc register_team
- Inputs: Team name, Manager full name, Username, Password (min. 6 characters).
- Creates the team, the login and a manager profile, then signs the creator in.

D. PROFILE SETTINGS & TEAM PAGE (replace the old Team & staff modal):
- PROFILE SETTINGS (ProfileView.vue, everyone): opened from your name at the
  bottom of the sidebar, or by tapping your name in the phone's top bar. No
  profile picture. Sections:
  * Name: display name (rpc update_my_display_name; past snapshots keep the old name).
  * Username: also the sign-in name (rpc update_my_username: 3-32 letters, numbers,
    dot, dash, underscore; unique; updates staff_profiles and the Auth login email
    <username>@checkingboard.internal). You stay signed in; sign in with the new
    username next time (also in the Leader ELD extension).
  * Password: current password + new password twice (rpc change_my_password: checks
    the current password, at least 6 characters). This device stays signed in, the
    person's other devices are signed out.
  * Phone alerts toggle for this device, and "Sign out of this device".
- TEAM PAGE (TeamManagementView.vue, managers; sidebar "Team", phone tab "Team"),
  two tabs (the last one opened is remembered in the browser):
  * Members (TeamMembers.vue): the roster with role, state and shift, and the
    account actions below. Your own row says to use Profile settings.
  * Attendance (AttendanceView.vue, see 16E D): month summary, every check-in,
    "Late after" rule and the reminders switch.
  Staff on phones keep their own "Team" tab (their shift-mates and managers).
- Managers only (each is a database function that checks the caller is an active
  manager of the same team):
  * "Create Staff Account" (rpc create_staff_account): name, username, initial
    password, role (staff / manager).
  * "⭐ Promote to Manager" / "Demote to Staff" (rpc set_staff_role).
  * "🔑 Reset Password" (rpc reset_staff_password): also signs that user out everywhere.
  * "Deactivate" / "Activate" (rpc set_staff_active): blocks the login and all data
    access; history is kept. Deactivating also takes the person off their shift and
    removes their phones from push alerts (reactivating does not put them back on a
    shift). Managers cannot change their own role or status.
- Deactivated members are listed ONLY in Team -> Members (marked "Deactivated"). Everywhere else
  (shift cards and pickers, Logs staff filter, Statistics per-staff table,
  Attendance person filter and month summary, notification recipients, on-duty list,
  Team page) shows active members only. Their past records stay: log rows and
  check-in rows keep their name snapshot, and team / shift totals still count them.
- There is no "switch user" button: with real logins you sign in as yourself.

E. SIGN OUT & STAYING SIGNED IN:
- "Sign Out" in the top bar or the modal ends the Supabase session on THIS device
  only (signOut scope 'local'); the person stays signed in on their other devices.
- Nothing else signs a person out in the app. A saved sign-in that can't be
  confirmed when the app opens (no connection, server not answering) shows
  "Reconnecting to CheckingBoard…" with a Sign out button and keeps retrying (and
  retries at once when the connection comes back) instead of showing the login.
- The login screen appears only when Supabase rejects the saved sign-in (revoked:
  password reset, deactivation, or Auth session limits set in the dashboard), the
  account is deactivated, or the person signs out.

16. ACTION-ONLY LOGS, SHIFTS & MANAGER PAGES (supersedes parts of section 14)
--------------------------------------------------------------------------------
A. WHAT IS LOGGED:
- A log record is written ONLY for a dispatch action, and those are recorded by the
  Leader ELD logging extension (see 16C), not from the board: SHIFT (Open Shift), CYCLE (Open Cycle), FIX_LOG, BREAK, DRIVER_CONNECTED
  (Connect). Status changes, quick checks (✓), transfers and driver / company
  add / delete are NOT logged. The activities INSERT policy rejects any other
  action_type. Older records of other types stay in the database but are not shown.

B. SHIFTS (Tashkent time, UTC+5, no daylight saving; src/config/shifts.js):
- Default hours: MORNING 07:00-15:00, AFTERNOON 13:00-23:00, NIGHT 23:00-07:00.
  Pages also show the hours converted to US Eastern for the day (follows EST/EDT).
- Custom hours: managers set each shift's start and end time, either the same every
  day or different per weekday. Stored in public.shift_hours (team_id, shift_code,
  weekday 1 = Monday ... 7 = Sunday of the day the shift STARTS, start_min / end_min
  = minutes after Tashkent midnight; end <= start means it ends the next day).
  Managers replace the whole set with rpc save_shift_hours([{shift_code, weekday,
  start_min, end_min}]); days without a row use the defaults. Members read their
  team's rows; nobody writes the table directly.
- Any number of people per shift. staff_profiles.shift_code holds each person's
  assigned shift. Managers change the whole schedule at once with rpc
  save_shift_schedule({MORNING:[ids],AFTERNOON:[ids],NIGHT:[ids]}): one shift per
  person, people left out are unassigned.
- Every activity is stamped by the database trigger (public.cb_shift_of(p_at,
  p_assigned, p_team), which reads the team's hours) with:
  * shift_code: the shift its author is assigned to at that moment; someone with no
    shift is placed by the clock. Of the shift runs that started yesterday or today,
    the one covering the moment wins (start inclusive, end exclusive); in an overlap
    the run that started first wins (by default 13:00-15:00 counts as MORNING).
    An action outside every run (early start, late finish, a gap between custom
    hours) goes to the nearest run.
  * shift_date: the WORK DAY = Tashkent date the chosen run started, so a shift past
    midnight belongs to the day it began. Old records were backfilled by the clock.
  src/config/shifts.js applies the same rule for the sidebar, board and Shifts page.
- Reassigning someone or changing hours later never changes past records.

C. MANAGER PAGES (top bar):
- Logs: managers see the whole team. Staff see their own actions plus the actions
  logged on their current shift by people currently on that shift; other shifts,
  unassigned people and managers stay hidden, and unassigned staff see only their
  own (enforced by the activities SELECT policy, so the sidebar and KPI counts follow
  the same rule). Pick a work day (◀ ▶ / date) and a shift (All / Morning /
  Afternoon / Night, managers); filter by staff (managers: anyone; staff on a shift:
  "Whole shift" or one shift-mate), action and driver/company. Each row shows the
  exact time in Tashkent and US Eastern, shift, staff, driver, action and note,
  plus per-action counts for the selection.
- Shifts: shift control panel. Three shift cards, each with its hours (Tashkent,
  today's shown in the card head with US Eastern) as one "Every day" range or seven
  weekday ranges ("Different per day" / "Same every day"; an end before the start is the next day),
  and a people list with remove buttons and a "+ Add a person…" picker (picking
  someone from another shift moves them). "On duty now" badge, unassigned list, one
  Save Schedule / Discard for people and hours together.
- Statistics: a date range picked on a calendar (up to 31 days, see 16B). Shows

  precision, office_radius_m integer, office_updated_at timestamptz,

16F. CHECK-IN / CHECK-OUT REMINDERS
--------------------------------------------------------------------------------
A. WHAT STAFF GET:
- A phone alert titled "Shift reminder" (iPhone shows "Shift reminder from
  CheckingBoard"), greeting them by their display name, 2 minutes before their
  shift starts ("Hey Nick, your shift is about to start. It's time to check in.")
  and 2 minutes before it ends ("Hey Nick, your shift is about to end. It's time
  to check out."). Tapping it opens the app on Check in.
- Check-in reminder: only if they have not checked in to that shift run yet.
  Check-out reminder: only if they are checked in to that run and not out yet.
- Needs phone alerts turned on on that phone (Notifications page) like any push.
- Goes to active members with a shift (managers too, if they are on a shift).

B. MANAGER SWITCH: "Check-in / out reminders" on Team -> Attendance (PC and phone),
   on by default, for the whole team (rpc set_shift_reminders, managers only). The
   switch is hidden until the database script has been re-run.

C. HOW IT RUNS (no app needs to be open):
- pg_cron calls the shift-reminders Edge Function every minute (pg_net HTTP POST
  with the secret header x-cron-secret).
- The function checks the secret against public.cb_cron_config, then calls
  claim_shift_reminders(2): every active member on a shift, in a team with reminders
  on, whose shift start / end (team hours via cb_shift_run, runs starting yesterday,
  today or tomorrow) is less than 2 minutes away. Each reminder is recorded in
  shift_reminders_sent (staff, CHECK_IN / CHECK_OUT, event time) and returned once;
  rows older than 2 days are cleared. The function looks up each person's display
  name and sends them their own Web Push through supabase/functions/_shared/push.ts,
  which send-push uses too.

D. DATABASE (supabase_schema.sql section 7E, safe to re-run):
- teams.shift_reminders_enabled (default true); tables shift_reminders_sent and
  cb_cron_config (RLS on, no policies, no client grants).
- rpc set_shift_reminders (managers); claim_shift_reminders (service role only);
  setup_shift_reminders(project_url) (run by you in the SQL Editor only): turns on
  pg_cron and pg_net, stores the URL and a new random secret, and schedules the job
  'cb-shift-reminders' every minute (running it again replaces the job and secret).
- set_staff_active(false) now clears the person's shift and deletes their push
  subscriptions; the script also clears the shift of anyone already deactivated.

E. SETUP (once, after phone alerts work, see README "Shift reminders"):
1. Re-run supabase_schema.sql.
2. npx supabase functions deploy shift-reminders --no-verify-jwt
3. In the SQL Editor: SELECT public.setup_shift_reminders('https://<ref>.supabase.co');
To stop the schedule entirely: SELECT cron.unschedule('cb-shift-reminders');

F. TESTS: 28 (reminder switch: managers only), 29 (deactivation clears the shift and
   the phones; reminder internals are not reachable by app users).
